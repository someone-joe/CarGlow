# CarGlow 自动化测试用例库

> 用途：功能设计阶段已收口，本文件夹是**测试阶段的唯一用例管理入口**。
> 本目录只放**用例设计与测试规划**；可执行脚本不在这里（按端归属，见下文「执行规划」）。
>
> 依据文档（冲突时按优先级靠前者）：`订单状态机规则表.md`（SSOT）> `openapi.yaml`（SSOT）> `洗车项目PRD.docx` > `洗车项目技术方案.md` > `洗车项目商业计划书.docx` > `小程序需求文档拆解.docx`。

## 一、范围与优先级定义

优先级对齐 PRD 表 5-1：

| 级别 | 含义 | 测试策略 |
| --- | --- | --- |
| P0 | 开业必需（缺失则业务停摆） | **100% 覆盖**：正向 + 全部边界/异常/越权/幂等 |
| P1 | 体验与效率（影响转化/复购） | 正向 + 关键边界，通过率要求 ≥95% |
| P2 | 规模化（多点位复制） | 本期不设计用例 |

- **接口自动化**：按用户要求做**全面**覆盖——正向 + 边界 + 异常 + 安全，暂不关注性能（P95/并发容量等留待单独的性能测试规划）。
- **UI 自动化**：P0 主业务用例为主，少量 P1 边界，不覆盖 P2。

## 四、测试环境与数据基线

### 4.1 环境（本地 dev 栈）

| 组件 | 地址 | 说明 |
| --- | --- | --- |
| 后端 API | `http://localhost:8080` | RuoYi + ruoyi-wash；`mock-pay` 开启（`wash.pay.mock-enabled`） |
| MySQL | `127.0.0.1:3306/carwash` | root / carglow_dev |
| Redis | `127.0.0.1:6379` | 产能/锁/token |
| 微信开发者工具 | 已配置服务端口 + 测试号 appid | UI 自动化用（wechatide） |
| 小程序 | `dist/dev/mp-weixin` | dev watch 产物 |

### 4.2 数据基线（造数原则）

1. **所有造数必须走接口/状态机**，禁止直接 `UPDATE wash_order.status`（会让流转日志与状态错位，已发生过）。
2. 会员：dev 模式任意 `code` 登录得 `dev-openid`；师傅：`W001`（本地口令以 seed 为准）。
3. 站点/小区/机柜/格口/服务取 seed 现有数据；**每轮跑完执行格口与产能复位**（`wash_seed_dev.sql` 末尾语句），否则联调占满后下单报 B2003。
4. 用例间数据隔离：不同用例用不同车牌/备注前缀标识，便于清理与排查。
5. 金额断言一律**分**；时间断言容忍时钟漂移（±2s）。

### 4.3 已知限制（影响用例预期，不是缺陷）

- 真实微信支付/退款未接：`mock-pay` 为 dev-only；退款走 mock 渠道。相关用例仅验证到「渠道已调用、状态机已推进」。
- 柜机硬件未接：`device-callback/v1/slot/deposit` 用脚本模拟柜机行为。
- 工位（bay）表未建：作业台 `bayNo`/`sopStep` 为 null，属预期。
- 后台登录路径是 `/login`（不是 `/admin-api/login`）。

## 五、用例编号规则

| 前缀 | 模块 |
| --- | --- |
| API-A ~ API-Q | 接口用例（按模块分段，见接口文档目录） |
| UI-C / UI-W / UI-A | UI 用例（C 端 / 师傅端 / 后台） |

每条用例字段：编号、标题、优先级、前置/数据、步骤、预期（含错误码）、依据（文档章节或 openapi 路径）。

## 六、通过标准（对齐 PRD 12 验收）

1. P0 用例通过率 **100%**；P1 ≥95%。
2. 全链路穿测：≥20 单真实订单跑完整流程，且至少覆盖：1 次退款、1 次重洗（QC_FAIL→WASHING）、1 次紧急取钥匙、1 次柜机离线应急（模拟回调失败/超时）、1 次超产能顺延（WAIT_KEY→次日）。
3. 安全：越权（水平+垂直）用例全通过；脱敏字段（手机号 `138****1234`、openid `dev-****enid`）断言通过；操作日志只增（无删除用例）。
4. 回归：每条用例须可在干净数据基线上重复执行（见 4.2 复位要求）。

## 七、执行规划（后续单开任务，本文档不含可执行脚本）

> 按项目红线「禁止新增依赖」：执行框架选型需先提方案获批准后再动。预选方案（按推荐序）：

| 层 | 方案 | 现状 |
| --- | --- | --- |
| 接口 | Node 脚本（`node:test` + 内置 `fetch`，零新增依赖）驱动 `localhost:8080` | 仓库已有 Node 生态；`sim-flow.ps1` 是前身（仅 Windows） |
| 接口 | JMeter / Postman+Newman | 免改仓库依赖，适合非开发执行 |
| UI | wechatide CLI（官方，已跑通冒烟） | `carwash-mp/test/automator/smoke.sh` 已验证 |
| UI（后台） | Playwright | **缺基建**（carwash-admin 无测试目录），需先立框架 |

脚本落位遵循「按端归属」：接口脚本进 `carwash-server`（或根 `scripts/` 若跨端编排），UI 脚本进 `carwash-mp/test/`，后台 UI 脚本进 `carwash-admin/`。
